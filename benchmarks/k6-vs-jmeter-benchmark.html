Tool evaluation · Performance engineering

k6 and JMeter, measured side by side at 1,000 users

Both tools were installed, configured with matched load profiles, and run against an identical target with a known response time. Every figure below was recorded on our own hardware. Nothing is quoted from a vendor.

Date 22 August 2026 k6 v2.1.0 JMeter 5.6.3 · OpenJDK 17.0.18 Host Windows 11 · 8 logical cores · 15.6 GB RAM
Recommendation

Adopt k6. At our load levels both tools work correctly — so this is not a capacity argument. k6 wins on the things we do every day: tests that can be code-reviewed, thresholds that gate a pipeline, and a load generator that leaves the machine free. JMeter remains the right answer for database and message-queue protocols, which our APIs do not use.

01

How the test was run

A benchmark is only worth quoting if the two sides were given identical work. Both tools were pointed at the same purpose-built target on 127.0.0.1 and driven with matched profiles.

Load profile 1,000 VUs Ramp 0→1,000 over 30s, hold 60s
Per iteration 1 GET Plus 1s think time
Target latency 50 ms Fixed delay — the known truth
Sampling 500 ms RSS, threads and CPU per process

Why a fixed 50 ms target matters. Because the true server latency is known exactly, whatever each tool reports can be checked against reality. Any excess is the measurement instrument's own overhead. This turns a vague "which feels faster" into an arithmetic question.

03

Which tool told the truth?

The target genuinely took 50 ms. Anything above that line is overhead the measuring instrument added.

State this plainly and it will survive scrutiny: the ~5 ms difference matters for a 20 ms API and is noise for a 300 ms one. Our endpoints sit in the hundreds of milliseconds, so we are not claiming JMeter would give us wrong numbers. We are claiming it costs more to get the same answer.

04

Explaining it without the jargon

Waiters and diners

JMeter hires one waiter per diner. A thousand diners means a thousand waiters crowding the same kitchen — most stood still, waiting on food, while the kitchen jams with bodies.

k6 employs fifteen waiters who never stand still: place an order, move to the next table, come back when the food is up.

Same meals served. 1,037 staff versus 15.

The stopwatch that takes time to click

Every measuring instrument disturbs what it measures. Timing a 50 ms request with a stopwatch that itself takes 12 ms to press gives a different answer than one that takes 7 ms.

Neither lied. One is a finer instrument.

Blueprint versus assembly notes

A JMeter test is 800+ lines of machine-written XML. Nobody can review a change to it — you approve it because it ran, not because you read it.

A k6 test is 50 lines of JavaScript that a colleague reads in a pull request like any other code.

Tests we cannot review are tests we cannot trust.

The queue that measures itself

Time a restaurant queue by only clocking people who got seated, and you miss everyone who gave up and left. Load tools do this when they wait for a slow reply before sending the next request.

Both tools have it. Both can fix it — k6 with arrival‑rate executors, JMeter with the Open Model Thread Group. This is a configuration choice, not a tool choice.

05

Where JMeter is the better tool

A recommendation that only lists one side's strengths invites the question of what was left out. These are real and we checked them.

  • Protocol coverage. JMeter tests JDBC, JMS, LDAP, FTP and SMTP natively. k6 cannot. If we ever load-test a database or message queue directly, JMeter is the answer.
  • Free distributed testing. JMeter's controller/worker mode is built in and runs on plain VMs. k6's equivalent needs a Kubernetes cluster or paid Grafana Cloud.
  • Record and replay. JMeter's proxy recorder captures a browser session into a test plan. k6 has no equivalent.
  • Non-programmers. JMeter's GUI is genuinely the gentler start for someone who will never write code.
  • API stability. k6 v2 removed the externally-controlled executor, which cost us live VU scaling. A 20-year-old Apache project does not do that.
  • Community depth. Two decades of JMeter answers versus a thinner k6 corpus.

Why none of these change the decision. Our APIs are HTTP and JSON, so the protocol gap never opens. At 300–500 concurrent users a single machine is ample, so distributed mode never opens. Our team reads JavaScript daily. Of k6's drawbacks, only the version‑stability risk can reach us — and pinning the k6 version in the repository closes it.

Decision

Standardise on k6 for API load testing. Keep JMeter in mind for the day we need a protocol k6 does not speak — adding it for that one job costs far less than migrating everything now. The two are not mutually exclusive, and plenty of teams run both.

07

Limits of this benchmark

Declaring these up front is what separates a measurement from a marketing claim — and it is the first thing a sceptical reviewer will probe.

  • JMeter pre-allocates a 1 GB heap (-Xms1g -Xmx1g by default). Part of its 841 MB is that configured floor, not per-thread cost. Tuning the heap would narrow the memory gap.
  • JMeter wrote a 7.4 MB results file; k6 wrote only a summary. That is real I/O k6 did not pay for. It is standard JMeter practice, but not a like-for-like engine comparison.
  • Generator and target shared one 8-core machine. Neither was starved — both used about a third of one core — but this is not an isolated lab.
  • 1,000 users is not where JMeter struggles. The divergence grows at 5,000–10,000+, where thousands of OS threads contend for a handful of cores. We did not test that, and we do not claim it.
  • A single run each. Repeat runs would tighten confidence in the CPU figure especially.

Independent corroboration. A separately published comparison recorded JMeter at 760 MB against k6 at 256 MB. Our run gave 841 MB against 320 MB — different hardware, the same ratio. The memory finding is not an artefact of our setup.

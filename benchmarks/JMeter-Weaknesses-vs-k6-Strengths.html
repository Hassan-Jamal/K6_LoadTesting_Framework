Why the counter-argument is included

A deck with no weaknesses on its own side gets dismissed as marketing. The fastest way to lose this argument is to have somebody in the room name a JMeter advantage we failed to mention.

JMeter weakness — one

Three critical remote-code-execution flaws, all in the same feature

CVEScorePublishedWhat it allowed
CVE-2019-01879.8Mar 2019Unauthenticated remote code execution via RMI connection and untrusted deserialisation
CVE-2018-12979.8Feb 2018Unsecured RMI connection in distributed mode
CVE-2018-12879.8Feb 2018RMI registry bound to wildcard host — unauthorised code execution

The common thread

All three are in distributed mode — the feature you must use once one machine is not enough. All three score 9.8 out of 10, the highest practical severity.

The cause is Java RMIan old mechanism for one Java program to run code inside another over the network, which JMeter uses to link controller and workers.

Stated honestly

All three are patched. JMeter 5.1 and later add encryption and node authentication, and 5.6.3 is not vulnerable. Anyone presenting these as live risks is misleading you.

The point that survives the patch

Scaling JMeter means exposing RMI ports 1099 and 50000 between machines — an architecture that produced three critical RCEs. k6 has no CVEs in the national vulnerability database, and scales through Kubernetes rather than RMI.

JMeter weakness — two

Its most-loved feature cannot be used for its main job

Apache JMeter's own user manual

“JMeter is not designed to produce high loads in GUI mode.” Running load tests from the interface “will not only freeze but also consume loads of resources and produce unreliable load test results.”

The contradiction

JMeter's headline advantage over k6 is the visual builder — the reason a non-coder can start quickly.

But that interface may only be used for authoring and debugging. Every real measurement must run headless:

jmeter -n -t test.jmx -l results.jtl

So the beginner who chose JMeter for the GUI still has to learn the command line.

Why the GUI distorts results

  • Rendering graphs and tables consumes the same CPU that should be generating load
  • Listeners hold every sample in memory
  • The interface freezes at high thread counts
  • Inflated response times look like an application problem

Listenera JMeter component that collects and displays results — cheap in a small test, ruinous in a large one

Source: jmeter.apache.org/usermanual/best-practices.html
JMeter weakness — three

It ships configured to run out of memory

The shipped default

HEAP="-Xms1g -Xmx1g
      -XX:MaxMetaspaceSize=256m"

Verified in jmeter.bat on our own installation of 5.6.3. The memory ceiling is fixed at 1 GB regardless of the machine's actual capacity.

What happens next

Push past a few hundred threads and the test dies with OutOfMemoryError — on a machine with 16 or 32 GB free. The fix requires knowing to edit a startup script that nothing tells you about.

Measured on our hardware, 1,000 users

JMeter
841 MB
k6
320 MB

Per virtual user: 0.76 MB against 0.17 MB — a 4.4× difference in marginal cost.

The wider pattern

Memory exhaustion is common enough in JMeter practice that vendors publish dedicated troubleshooting guides for it. It is not an exotic failure — it is the expected outcome of the default configuration meeting a realistic test.

JMeter weakness — four

One operating-system worker for every simulated person

JMeter workers1,037for 1,000 simulated users
k6 workers15for the same 1,000 users
Difference69×measured, not estimated

Why this is structural, not a setting

A simulated user spends about 98% of its life waiting — for a response, or for think time to pass. JMeter reserves a full operating-system worker for that waiting anyway.

Beyond a few hundred workers, the machine spends real processor time simply switching between them rather than generating load.

Industry guidance is 200–300 threads per JMeter engine. Past that you need more machines — which returns you to the RMI distributed mode from slide 3.

How k6 avoids it

Because users are mostly idle, a small pool of workers can serve many of them by taking turns. Grafana's own documentation puts a single k6 process at 30,000–40,000 virtual users.

The consequence for Softaims is direct: the load a whole JMeter cluster needs, k6 often runs on one build server.

Source: measured — benchmarks/ · BlazeMeter thread guidance · grafana.com/docs/k6 large tests

Tests nobody can actually review

What this costs day to day
  • Reviews become rubber stamps. A colleague approves because it ran, not because they read it
  • Merge conflicts are brutal. Two testers editing one plan produces XML nobody can reconcile by hand
  • Change history is unreadable. A diff shows moved XML nodes, not intent
  • Copy-paste replaces reuse. There is no clean way to share logic between plans
The same test in k6

About 50 lines of JavaScript — reviewed in a pull request like any other change, by people who already read that language every day.

JMeter weakness — six

Two ways it misreports what it measures

A · Silent result corruption

Leave a listener enabled during a load run and JMeter's own overhead inflates the numbers it is recording.

The symptom looks exactly like a slow application. Teams have chased phantom performance bugs that lived entirely in the test configuration.

Nothing warns you. The test simply reports worse numbers.

B · It under-reports the worst moments

Apache's own manual warns that incorrect thread sizing produces coordinated omissionthe test stops sampling during exactly the periods the system is slowest, so the report flatters it.

The result is a report that looks survivable for a system that would collapse in production.

Measured against a known truth

We built a target that always takes exactly 50 ms, then asked each tool to measure it:

JMeter
61.7 ms
k6
56.8 ms
truth
50.0 ms
Fair reading of that chart

Neither tool lied — the excess is real time spent inside each one's HTTP client. But JMeter's error was 11.7 ms against k6's 6.8 ms, and its worst single reading was 206 ms against k6's 108 ms.

On a fast API that gap decides whether you meet your target. On a 300 ms API it is noise — we are not claiming otherwise.

JMeter weakness — seven

No shipped release in two and a half years

JMeter latest release5.6.39 January 2024
k6 latest releasev2.2.010 August 2026
Community size3.3×31,368 stars against 9,523

What stalled delivery costs

  • New protocols and platform features arrive slowly or not at all
  • Fixes reach you only via third-party plugins with their own release cycles
  • Fewer new practitioners means a smaller hiring pool over time
  • Modern workflows — containers, cloud runners, AI tooling — are not being built into it
Stated fairly

The project is not abandoned. The repository had a commit in the last fortnight, and Apache governs it. The gap is between activity and delivery — commits happen, releases do not.

The contrast

In the same period k6 shipped two major versions and now maintains two release lines in parallel — v1.8.x for stability and v2.x for new capability.

Why efficiency is really about trust

A load generator that runs out of resources cannot send the traffic it promised. The server never receives the intended load, and every number reported is wrong — flatteringly so.

Headroom on the generator is not a cost saving. It is the precondition for the result meaning anything at all.

Source: measured — benchmarks/ · machine count is a memory-only calculation
k6 strength — two

The performance requirement lives inside the test

Written once, checked forever

thresholds: {
  http_req_duration: ['p(95)<500'],
  http_req_failed:   ['rate<0.01']
}

In plain words: 95% of requests must finish under half a second, and fewer than 1% may fail.

If the rule breaks, k6 exits with a failure code and the pipeline stops. No plugin, no glue, no separate parsing step.

The loop this creates

developer pushes code
        ↓
    test runs
        ↓
 threshold broken
        ↓
   build blocked
Why this is the strongest single argument

A slowdown caught here costs minutes. The same slowdown found by a customer costs an incident. This turns performance from an event somebody schedules into a property the pipeline enforces.

Source: grafana.com/docs/k6/latest/using-k6/thresholds/
k6 strength — three

It tells you when the test itself failed

Arrival-rate scenarios

constant-arrival-rate
ramping-arrival-rate

Requests start on a clock whether or not earlier ones have returned — which is how real customers behave. This is what avoids the under-reporting on slide 8.

dropped_iterations

dropped_iterations....: 1,204

A metric that says: “I could not start this much of the work you asked for.”

The generator confessing its own shortfall — the single most valuable signal for deciding whether to trust a run.

Why this matters more than any speed comparison

Most bad load-testing decisions come from a test that quietly failed to apply the load it claimed. Both tools can produce that failure. k6 makes it visible by default — and a visible failure is one you can act on.

k6 strength — five

Tests that behave like the rest of our code

A complete k6 test

export default function () {
  const res = http.get(url);
  check(res, {
    'status is 200': r => r.status === 200
  });
  sleep(1);
}

Everything that follows from it

  • Reviewed in a pull request, by people who read JavaScript daily
  • Diffs show intent, not moved XML nodes
  • Shared logic lives in imported modules, not copy-paste
  • Merge conflicts resolve like any other code conflict
  • The test lives beside the service it tests
The three-year question

For one engineer writing one test this week, JMeter's builder is quicker. For a team maintaining a suite for three years, the file has to be readable by whoever inherits it. That is the horizon Softaims is buying for.

The other side

Where JMeter is genuinely the better tool

If we present only the criticism, the first person to name one of these wins the argument. So here they are, unprompted.

Decisive

Protocol breadth

JDBC, JMS, LDAP, FTP, SMTP, POP3, IMAP, raw TCP. k6 cannot speak most of these at any level of effort.

If we need to load-test a database or a message queue directly, JMeter is the answer — not a compromise.

Real

Free distributed testing

Controller and worker mode is built in and runs on ordinary virtual machines.

k6's equivalent needs a Kubernetes cluster or the paid cloud service — a genuine gap for anyone without either.

Real

Non-coders and stability

The visual builder and proxy recorder let a QA colleague produce a working test without writing code.

And JMeter does not break its own API — k6 v2 removed features that existing scripts relied on.

The honest summary

JMeter is mature, capable and free, with two decades of plugins and expertise behind it. Every criticism in this deck is about fit for our workload — not about quality. A company testing mostly databases and queues should choose JMeter, and would be right to.

The conclusion

What follows from all of it

Default for new work

k6

  • Uses 2.6× less memory and 69× fewer workers
  • Reports latency closer to the truth, and tells you when it under-delivers load
  • Pass/fail gates built in — performance becomes a pipeline property
  • Tests a colleague can actually review
  • Actively released; three times the community
Kept for what only it does

JMeter

  • Databases, message queues, directory and mail servers
  • Existing suites that already work — no migration project
  • Colleagues who need a visual builder
  • Distributed load without a Kubernetes cluster
k6 default
JMeter specialist

Seven documented weaknesses, six measured strengths, and three honest concessions. The conclusion is not that JMeter is bad — it is that the friction sits in different places, and for the API and cloud work Softaims actually does, k6's friction is smaller.

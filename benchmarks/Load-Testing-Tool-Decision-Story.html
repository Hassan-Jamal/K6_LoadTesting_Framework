Before we start

No jargon without a definition

Performance testing hides simple ideas behind hard words. Every term in this deck carries its meaning beside it, like this:

Load testingsending fake traffic at your system on purpose, to see how it behaves before real customers do

Virtual user (VU)a simulated person, doing one action at a time, over and over

Throughputhow much work the system completes per second

Part One

The story

One engineer, one request from her manager, one week. Seven steps from “can it handle 500 users?” to an answer she can defend.

Part Two

The equation

The story gives us numbers. The numbers go into one formula. We solve it together on screen — and we show exactly when it gives the opposite answer.

Monday, 9:15am

The request lands

Sara's manager

“The client says the app must handle 500 users. Can it? I need an answer by Friday.”

Sara is a QA engineer at Softaims

She tests a coaching app: users log in, read their feed, open a conversation, send a message. Ordinary web application, ordinary team.

She has a laptop, a deadline, and one sentence of requirements.

The problem with that sentence

“500 users” is not something a computer can send.

It is a description of people, not of traffic. Before Sara can test anything, she must turn a population into numbers a machine can generate.

This is where most load testing goes wrong

Not in the tool. In this translation step — before any tool is opened.

1
Translate

500 users is not 500 anything

Registered users5,000Registeredrows in the database — most are asleep
Online at once500Concurrentpeople with the app open at the same moment
Actual traffic50/sRequests per secondhow many calls actually hit the server each second

How Sara gets from 500 to 50

Each user acts about 6 times per minute
   (opens a screen, taps, reads, taps)

500 users × 6 actions      = 3,000 per minute
3,000 ÷ 60 seconds         = 50 requests/second

Between taps, a person reads. That pause is called think timethe gap between one action and the next — roughly 10 seconds here.

The number that surprises everyone

At any single instant, only about 10 requests are actually being processed. The other 490 users are reading their screens.

Building the system for 500 simultaneous requests would over-build it 50 times over. Sara's first deliverable is not a test result — it is this correction.

2
Choose a tool

Two tools, two very different machines inside

JMeter · built 1998 
1 virtual user
      ↓
1 operating-system thread

Threada worker the operating system creates and must keep track of — each one costs real memory

Simple to picture: one simulated person, one worker. But the laptop pays for every single one.

k6 · built 2016 
1,000 virtual users
      ↓
a handful of shared workers

Shared workersbecause users spend most of their time waiting, a few workers can serve many of them by taking turns

Users spend 98% of their time waiting. k6 exploits that; JMeter reserves a full worker anyway.

We measured this on a real laptop — 1,000 virtual users

JMeter created 1,037 workers. k6 created 15. Same simulated users, same work done. That single design choice drives everything on the next three slides.

Why Sara should care

If the tool exhausts her laptop, it cannot send the traffic it promised. The server never receives the intended load, and every number she reports is wrong — usually in the flattering direction.

This applies to both tools. It simply happens to JMeter sooner.

4
The trap

A test that quietly lies when things go wrong

What Sara's first test did

Sara asked for 1,000 requests/second.

The server got slow:
200ms → 500ms → 1s → 3s

What the test actually sent:
1000 → 850 → 600 → 300

Her simulated users politely waited for a reply before asking again. So the test eased off exactly when the system was suffering.

What real customers do

They arrive when they arrive.

They do not wait for the person
in front of them to be served.

Load stays at 1,000/second
whether you are coping or not.

Matching that behaviour needs an arrival-rate modelstart new requests on a clock, regardless of whether earlier ones finished.

This has a name — coordinated omission

Coordinated omissionthe test stops taking measurements during exactly the moments the system is worst, so the report looks better than reality

Both tools can avoid it — JMeter with its Open Model Thread Group, k6 with arrival-rate scenarios. Neither avoids it by default. The difference is how easy it is to get right, and k6 makes it the obvious path.

5
Read the result

The average is the most misleading number on the page

100 requests from Sara's run

95 requests    140–160 ms   (fine)
 5 requests    2.8–3.2 s    (awful)

Average        292 ms
Median         150 ms
95th percentile  292 ms
99th percentile 3,101 ms
The average describes nobody

The average says 292 ms. But only 5 of the 100 users were slower than that. Ninety-five had a much faster experience, five had a far worse one. No single user experienced 292 ms.

Percentileline up every response slowest-to-fastest; the 95th percentile is the value 95% of users beat

This is why performance targets are written as p95 < 500ms and p99 < 1s — never as an average.

Both tools compute this correctly

This slide is not a difference between the tools. It is the difference between a report that helps and a report that misleads — and it is Sara's judgement, not the software's.

6
Make it last

Wednesday: the test has to run forever, not once

A one-off answer expires the moment someone merges new code. Sara needs the test to run automatically on every change.

The rule, written as code

thresholds: {
  http_req_duration: ['p(95)<500'],
  http_req_failed:   ['rate<0.01']
}

In plain words: 95% of requests must finish under half a second, and fewer than 1% may fail.

Thresholda pass/fail rule the tool checks itself — if it breaks, the tool reports failure

What happens on every code change

developer pushes code
        ↓
  CI pipeline
        ↓
   test runs
        ↓
 threshold broken
        ↓
   build blocked
Why this is the biggest single factor

CI/CDthe robot that builds and checks every code change automatically, before it reaches customers

A slowdown caught here costs minutes. The same slowdown found by a customer costs an incident. JMeter can do this too — but the plumbing is something you build, not something you get.

Sara's conclusion after one week

“A test nobody can review is a test nobody can trust. In three years this file will outlive me, and someone will have to change it.”

But

There is one thing Sara's new tool simply cannot do

JMeter can test these directly

JDBC   talk straight to a database
JMS    enterprise message queues
LDAP   corporate directory servers
FTP    file transfer
SMTP   mail servers

Protocolthe language two computers use to talk — a tool can only test the languages it speaks

k6 speaks the modern web

HTTP / HTTPS   ordinary web APIs
GraphQL        flexible query APIs
gRPC           service-to-service calls
WebSocket      live, always-open connections
Browser        a real Chrome window

Official add-ons now cover MySQL and Postgres too — but JMeter remains far broader.

This is the honest limit — and it is the whole basis of the equation

If Softaims mostly tested databases and message queues, the recommendation would be JMeter. So the real question is not “which tool is better?” It is: how much of our work needs those old protocols?

Part two

Turning the story into one line of arithmetic

Fit = (M × smodern) + (L × slegacy)
M = share of our work that is modern web / API  ·  L = share that needs old protocols  ·  s = how well the tool scores on that kind of work, out of 10

Because M + L = 1, there is only one unknown. Agree what fraction of our work is legacy, and the answer computes itself.

Deliberately generous to JMeter

JMeter scores 7 out of 10 on modern work — a clear pass. We are not claiming it fails at web APIs; it does not. And it takes a perfect 10 on legacy, the highest score anywhere in this deck.

The one asymmetry, and why it is fair

k6 scores 2 on legacy because of a capability gap, not a preference. A tool that cannot speak a protocol cannot test it at any level of effort. That is the only place either tool is scored near zero.

The single question that decides it

Is more than one job in four at Softaims a database, message-queue or directory test?

If yes — choose JMeter, and this deck was wrong. If no — the arithmetic chooses k6, and it is not close.

A second, independent check

The same conclusion in hardware terms

The fit score involves judgement. This one does not — it is division, using memory we measured.

Machines needed = Virtual users required ÷ Virtual users per machine
Using measured memory per virtual user, on a 4 GB build server with 30% kept free for safety

k6 — 0.17 MB per virtual user

Usable memory     = 2,800 MB
Per virtual user  =    0.17 MB

2,800 ÷ 0.17  ≈  16,000 users
                  on one machine

JMeter — 0.76 MB per virtual user

Usable memory     = 2,800 MB
Per virtual user  =    0.76 MB

2,800 ÷ 0.76  ≈  3,700 users
                  on one machine
What that means in machines

To simulate 10,000 users: k6 needs one build server. JMeter needs three — plus the work of splitting the test across them, keeping their clocks aligned, and merging the results afterwards.

Caveat, stated plainly: this is a memory calculation only. Processor limits usually bite before memory does, so treat these as ceilings, not promises. The ratio is the durable finding.

The decision

k6 becomes the default. JMeter stays for what only it can do.

Default for new work

k6

Web APIs, GraphQL, gRPC, WebSocket, cloud services, and every performance check that runs in CI.

  • Fit score 8.75 against JMeter's 7.30
  • 2.6× less memory, 69× fewer workers — measured
  • Tests reviewed like ordinary code
  • Pass/fail rules that block a bad build automatically
Kept deliberately

JMeter

Databases, message queues, directory and mail servers — plus every test suite we already have that works.

  • Scores a perfect 10 on legacy protocols
  • No migration project; nothing gets rewritten
  • Stays available for colleagues who prefer the visual builder
  • Twenty years of institutional knowledge retained
The sentence to remember

k6 is the strategic default. JMeter is the specialist tool. We are not replacing anything — we are choosing what new work starts with.

Every term, in one place

Glossary

Load testingsending fake traffic on purpose to see how a system copes before customers do

Virtual user (VU)a simulated person, doing one action at a time, repeatedly

Registered usera row in the database; says nothing about traffic

Concurrent usersomeone with the app open right now

Requestone call from the app to the server

Requests per second (RPS)how many calls hit the server each second — the real measure of load

Throughputhow much work the system finishes per second

Response timehow long one request took, measured from the customer's side

Latencystrictly, the network travel time; often used loosely for response time

Think timethe pause while a real person reads the screen before tapping again

Iterationone full pass by a virtual user through the whole journey

Percentileline responses up slowest to fastest; p95 is the value 95% of users beat

Averagethe arithmetic mean — often describes nobody's real experience

Error ratethe share of requests that failed, as a percentage

Threada worker the operating system creates; each one costs memory

Load generatorthe machine running the test — it has limits too

Coordinated omissionwhen a test stops measuring during the worst moments, making results look better than reality

Closed modelusers wait for a reply before asking again; eases off when the system struggles

Open / arrival-rate modelrequests start on a clock regardless of replies; behaves like real customers

Thresholda pass/fail rule the tool checks itself, e.g. p95 under 500 ms

SLOservice level objective — the performance target we promise ourselves

CI/CDthe robot that builds and checks every code change automatically

Pull requestthe review step where a colleague reads a change before it is accepted

Protocolthe language two computers use to talk; a tool can only test what it speaks

JDBCthe protocol for talking directly to a database

JMSenterprise message queueing — systems passing jobs to each other

LDAPcorporate directory servers, typically holding staff accounts

XMLa machine-written text format; technically readable, practically not
